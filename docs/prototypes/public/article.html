Designing payment flows for unreliable networks

How we plan for dropped connections, retries and confirmations so people are never charged twice.

Placeholder article Sample technical writing to show the body styles.

A payment can fail in more places than the screen shows. The request can leave the phone and never arrive, arrive and never get a reply, or succeed while the reply is lost on the way back. On networks that drop often, each of these happens every day.

This article covers the patterns we start from when we design a payment flow, and why each one exists.

The problem with a single request

When a payment request times out, the app does not know what happened. Asking the person to try again is the most common answer, and the most dangerous one. Three outcomes are possible:

  • The request never reached the server, so nothing was charged.
  • The server charged the payment, but the reply was lost.
  • The server is still processing the payment.

Only the first one is safe to retry blindly.

Make every request safe to repeat

Each payment gets a payment_reference created on the device before the first attempt. The server treats a second request with the same reference as the same payment, so a retry can never charge twice. 

def submit_payment(client, payment):
    # Reuse the same reference on every attempt.
    reference = payment.reference
    for attempt in range(1, 4):
        try:
            return client.charge(reference=reference, amount=payment.amount)
        except NetworkTimeout:
            wait_before_retry(attempt)
    return check_status(client, reference)

Show the state, not a spinner

People need to know what is happening while the app waits. We design for three steps:

  1. Tell the person the payment is being sent.
  2. If it takes longer, say that we are checking with the payment provider.
  3. If we still have no answer, show the payment as pending and confirm it later.

The world is changing quickly, and the technology we use should be ready for where people are going, not only where they are today.

A retry policy to start from

Example retry policy for one payment
Attempt Wait before it What the person sees
First None Sending payment
Second 2 seconds Still sending
Third 5 seconds Checking with your payment provider
Status check After the third attempt Payment pending, we will confirm it

None of this is new, but it is easy to skip when the office network is fast. We test every payment flow on throttled connections before it ships.
